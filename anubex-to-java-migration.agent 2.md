### Anubex Framework Knowledge Base

The programs in this workspace were **auto-generated** by the **Anubex Migration Tools 3.0.0** from SAG Natural source code. They are NOT traditional COBOL — they contain a runtime framework layer (`NM--` prefix) that emulates Natural's behavior.

#### Code Structure Conventions

| COBOL Division/Section | Anubex Role |
|---|---|
| `WORKING-STORAGE SECTION` | Global persistent state — `COPY 'NMCONSTN'` (constants), `COPY 'NMGLOBAL'` (framework globals) |
| `LOCAL-STORAGE SECTION` | Per-invocation variables — `COPY 'NMLOCAL'`, program-specific copybooks, `DATA LOCAL` equivalents |
| `LINKAGE SECTION` | Parameters from caller via `NM--LINKAGE-PARAMETER` — maps to Natural `DEFINE DATA PARAMETER` |
| `PROCEDURE DIVISION` | Entry starts with `COPY 'NMINIT'`, ends with `COPY 'NMHELPSB'` or `GOBACK` |

#### Control Flow Mechanisms

| Anubex Pattern | Original Natural Construct | Meaning |
|---|---|---|
| `NM--LVL` | Execution nesting level | Tracks active FOR/REPEAT/READ loop depth |
| `NM--ESC` | ESCAPE control flag | `0`=normal, `1`=ESCAPE TOP (continue), `2`=ESCAPE BOTTOM (break), `3`=ESCAPE ROUTINE (return) |
| `GO TO ... DEPENDING ON NM--ESC` | Three-way branch | Maps to continue/break/return |
| `PERFORM NM--INCLUDExx-<pgm>` | Natural `INCLUDE <copycode>` | Inline copycode expansion (section at end of file with `COPY 'copybook'`) |
| `PERFORM NM--RDWORK0x-<pgm>` | Natural `READ WORK FILE x` | Work file read loop until EOF |
| `PERFORM NM--FIND0x-<pgm>` | Natural `FIND ... WITH ...` | Database FIND loop over matching records |
| `PERFORM NM--READ0x-<pgm>` | Natural `READ ... BY ...` | Database READ loop over ordered records |
| `NM--REPEAT0x-<pgm>` | Natural `REPEAT ... UNTIL` | Code loop with exit condition checked at end (→ `do { } while ()` or `while (true)` with `break`) |
| `NM--FOR0x-<pgm>` | Natural `FOR #var = start TO end STEP step` | Indexed loop with explicit counter, exit-test, and decrement/increment step |
| `NM--ON-ERROR SECTION` | Natural `ON ERROR` | Global error handler |
| `NM--TARGET-LOOP` + `NM--ESCAPE-BOTTOM` | Natural `ESCAPE BOTTOM (label.)` | Named break — break out of a specific outer loop, not just innermost → **Java: `break LABEL;`** |

#### CALLNAT Parameter Marshalling (NM--PARAMETER-BLOCK Pattern)

Anubex translates Natural's `CALLNAT 'subprog' <params>` into a parameter marshalling pattern using REDEFINES overlays:

```cobol
01  NM--PARAMETER-BLOCK PICTURE X(88).           ← Single shared byte buffer
01  PB--{PROGRAM}--1 REDEFINES NM--PARAMETER-BLOCK.  ← Overlay for 1st CALLNAT target
    02  P--001 PICTURE X(3).                      ← Parameter 1
    02  P--002 PICTURE X(8).                      ← Parameter 2
    02  P--003 PICTURE X(38).                     ← Parameter 3
01  PB--{PROGRAM}--2 REDEFINES NM--PARAMETER-BLOCK.  ← Overlay for 2nd CALLNAT target
    02  P--001 PICTURE X(2).                      ← Different parameter layout
    ...
```

**The marshalling sequence is:**
1. **Marshal IN:** `MOVE field TO P--001 OF PB--{PROGRAM}--n`
2. **Call:** `MOVE 'SUBPROG' TO NM--CALLED-PROGRAM` + `CALL NM--CALLED-PROGRAM USING NM--PARAMETER-BLOCK`
3. **Unmarshal OUT:** `MOVE P--001 OF PB--{PROGRAM}--n TO field`
4. For packed-decimal params: `CALL NM--BYTE-MOVE-PGM` replaces `MOVE` (byte-level copy required)

**Java migration:** Each PB--n overlay maps to a **method call with typed parameters** or a DTO. The P--001/P--002 fields map directly to method parameters and return values. NEVER create a Java "parameter block" byte buffer.

##### CALLNAT with Array Parameters (PB-- OCCURS Pattern)

When a CALLNAT passes array parameters, the PB-- overlay contains `FILLER OCCURS n TIMES` with subscripted fields:

```cobol
01  PB--{PROGRAM}--n REDEFINES NM--PARAMETER-BLOCK.
    02  FILLER.
        03  P--013 PICTURE X(8).                  ← Scalar parameter
        03  FILLER OCCURS 10 TIMES.               ← Array parameter group
            04  P--014 PICTURE X(2).              ← Array element
        03  P--015 PICTURE X(12).                 ← Scalar parameter
    02  FILLER.
        03  P--016 PICTURE X(8).                  ← Scalar parameter
        03  FILLER OCCURS 10 TIMES.               ← Another array parameter
            04  P--017 PICTURE X(6).
            04  P--018 PICTURE X(2).
            ...
```

Marshalling uses `PERFORM VARYING` to copy each array element:
```cobol
PERFORM VARYING NM--LOOP-INDEX-1 FROM 1 BY 1 UNTIL NM--LOOP-INDEX-1 > 10
    MOVE P-O-LIGNE-1(NM--LOOP-INDEX-1) TO P--021 OF PB--{PROGRAM}--n(NM--LOOP-INDEX-1)
END-PERFORM
```

**Java migration:** Array parameters become `List<T>` or `T[]` in the method signature. Each `FILLER OCCURS n TIMES` group with multiple sub-fields becomes a **record/DTO list**:
```java
record AddressResult(String type, String code, String line1, String line2, ...);
List<AddressResult> results = addressService.findAddresses(personId, usageCodes);
```

##### PERFORM SUBROUTINE OF PROGRAM (SYS-SUBROUTINE Dispatch)

Natural's `PERFORM <subroutine> OF <program>` calls a specific subroutine within an external program. Anubex translates this by setting `SYS-SUBROUTINE` before the CALL:

```cobol
MOVE 'RECHERCHE-REF-76' TO SYS-SUBROUTINE
MOVE 'AGOZNLGI' TO NM--CALLED-PROGRAM
CALL NM--CALLED-PROGRAM USING BY REFERENCE NM--PARAMETER-BLOCK
INITIALIZE SYS-SUBROUTINE
```

Key differences from regular CALLNAT:
- `SYS-SUBROUTINE` is set **before** the call to select which subroutine to execute
- `SYS-SUBROUTINE` is **reset after** the call (`INITIALIZE` = clear)
- The called program dispatches internally based on `SYS-SUBROUTINE` value

**Java migration:** Map to a specific method on the called service:
```java
// PERFORM RECHERCHE-REF-76 OF AGOZNLGI
String ref76 = lgiLookupService.rechercheRef76(ref70);  // specific method, not generic dispatch
```
Do NOT create a Java dispatcher that switches on a string — call the specific method directly.

#### Anubex-Generated Helper Variables (H-- Pattern)

Variables prefixed with `H--` are **compiler-generated temporaries** for intermediate conversions:

| Pattern | Scope | Purpose |
|---|---|---|
| `H--{PROGRAM}--{n}` | Main program | Scratch buffer for type conversions, intermediate results |

##### Natural COMPRESS Semantics (CRITICAL for key construction)

Natural's `COMPRESS field1 field2 ... INTO target` has specific behavior that MUST be replicated exactly:

1. **Trailing spaces are stripped** from each source field before concatenation
2. Fields are joined with a **single space separator** by default
3. With `LEAVING NO SPACE` modifier, no separator is added between fields
4. The result is **left-justified and right-padded with spaces** to the target field width

**COBOL translation by Anubex:**
```cobol
CALL NM--COMPRESS-PGM USING BY REFERENCE compress-block, field1, field2, target
```

**Java translation:**
```java
// COMPRESS field1 field2 INTO target (with spaces)
String result = (field1.trim() + " " + field2.trim());
result = String.format("%-" + targetLength + "s", result);

// COMPRESS field1 field2 INTO target LEAVING NO SPACE
String result = (field1.trim() + field2.trim());
result = String.format("%-" + targetLength + "s", result);
```

**⚠️ KEY CONSTRUCTION WARNING:** When COMPRESS is used to build database lookup keys (MEC, TYCRS, etc.), the trimming behavior changes the key from what you'd expect with simple concatenation. ALWAYS trim before concatenating for keys.

##### Zoned Decimal Output Format (S9(m)V9(n) via Alpha REDEFINES)

When a numeric field with implied decimal (S9(m)V9(n)) is written through an alpha `PIC X` REDEFINES overlay, the output is in **zoned decimal format** — NOT a formatted decimal string:

| COBOL PIC | Value | Zoned Decimal Output | Java String Output (WRONG) |
|---|---|---|---|
| `S9(4)V9(7)` | 12.34 | `+00123400000` (11 chars) | `0012.3400000` ← WRONG |
| `S9(7)V9(2)` | 1234.56 | `+001234560` (10 chars) | `1234.56` ← WRONG |
| `S9(5)` | -42 | `-00042` (6 chars) | `-42` ← WRONG |

**Java implementation:**
```java
public static String zonedDecimal(BigDecimal value, int intDigits, int decDigits) {
    if (value == null) return pad("", intDigits + decDigits + 1);
    String sign = value.signum() >= 0 ? "+" : "-";
    BigDecimal abs = value.abs().setScale(decDigits, RoundingMode.HALF_UP);
    String unscaled = abs.unscaledValue().toString();
    int totalDigits = intDigits + decDigits;
    String padded = String.format("%" + totalDigits + "s", unscaled).replace(' ', '0');
    return sign + padded;
}
```

**Rule:** When the serializer encounters a field whose copybook shows `PIC X(n)` REDEFINES'd as `S9(m)V9(p)`, ALWAYS use `zonedDecimal()` format — never `toPlainString()` or `pad()`.

##### F_TABLES Value Parsing Pattern (Multi-Field TFI_VAL)

The `F_TABLES` table stores configuration/reference data with composite values in `TFI_VAL`. Each `TFI_CDTFI` (table code) has a DIFFERENT REDEFINES layout for TFI_VAL.

**Parsing methodology:**
1. Find the copybook for the specific TFI_CDTFI being queried
2. Map ALL fields at their exact byte offsets within TFI_VAL
3. Account for separator characters (typically `/` at offset boundaries)
4. Extract EACH sub-field at its precise offset, NOT by splitting on separators

```java
// Example: Parse TB273 (currency info) from TFI_VAL
public CurrencyInfo parseTb273(String tfiVal) {
    return new CurrencyInfo(
        tfiVal.substring(0, 3),       // CODE-LIB (offset 0-2)
        // offset 3 is separator '/' — SKIP IT
        tfiVal.substring(4, 19),      // LIB-ABRV (offset 4-18)
        tfiVal.substring(40, 42),     // DEV-ANC (offset 40-41)
        tfiVal.substring(43, 44),     // DEV-DEC (offset 43)
        tfiVal.substring(44, 45),     // STATUS (offset 44)
        tfiVal.substring(45, 46)      // MODE-COTATION (offset 45)
    );
}
```

**Rule:** NEVER use `String.split("/")` or similar to parse TFI_VAL — always use fixed-offset extraction based on the REDEFINES layout.

##### NM--EDIT-PGM Call Signature and Output Width (CRITICAL)

The `NM--EDIT-PGM` call has a specific parameter layout that determines output width:

```cobol
CALL NM--EDIT-PGM USING BY REFERENCE
  input-field,              ← Source data field
  BY VALUE input-length,    ← Length of input field (e.g., 18 for S9(18), 12 for P15.7)
  BY CONTENT '(N18)',       ← Natural format descriptor
  BY VALUE descriptor-len,  ← Length of descriptor string
  BY CONTENT 'ZZZZZZZZZZZZZZZZZ9',  ← Edit mask string
  BY VALUE mask-length,     ← Length of mask string (18 or 19)
  BY REFERENCE output-buf,  ← Output buffer (e.g., XWK-LIG-AVIS PIC X(151))
  BY VALUE buf-size         ← Buffer size (e.g., 151)
```

**⚠️ CRITICAL: The mask string length is NOT the output width.**

The output width equals the **mask-length parameter** (the `BY VALUE` that follows the edit mask `BY CONTENT`). For Natural numeric formatting:

| Decimals | Edit Mask | Mask Length | Mask Chars | Output Width |
|---|---|---|---|---|
| 0 | `ZZZZZZZZZZZZZZZZZ9` | 18 | 18 chars | **18** |
| 1 | `ZZZZZZZZZZZZZZZZ9,9` | 19 | 19 chars | **BUT NM--EDIT-PGM output is still 18** |
| 2 | `ZZZZZZZZZZZZZZZ9,99` | 19 | 19 chars | **BUT NM--EDIT-PGM output is still 18** |
| 3-7 | `Z...9,999...` | 19 | 19 chars | **BUT NM--EDIT-PGM output is still 18** |

Although the mask string for decimal formats has 19 characters, the NM--EDIT-PGM produces an **18-character output** where the comma replaces one digit position within the base 18-char layout. The comma takes one position FROM the 18-char width, it does NOT add an extra character.

The reason: the input to `NM--EDIT-PGM` for decimals is `XWK-COMM-VAL-NUM PIC S9(15)V9(7) PACKED-DECIMAL` (12 bytes, `BY VALUE 12`), which after DIVIDE has been scaled. The output format always occupies exactly the same number of character positions as the integer format (18 total display characters), with the comma consuming one of those positions.

**Java migration:** Always format numeric output to **18 characters** regardless of decimal count. The decimal comma is embedded within the 18-char width, not added to it:
```java
// For ALL decimal counts: width = 18
// Integer positions = 18 - 1 (comma) - decimals
formatDecimal(value, decimals, 18);
```

**DO NOT** count the characters in the edit mask string literal to determine output width — always use 18.

| Natural Statement | COBOL Pattern | What to Extract |

**Oracle-Specific SQL Patterns (MUST handle during migration):**

| SQL Pattern | Purpose | Java Migration |
|---|---|---|
| `NVL(:field, ' ')` | Null-safe field comparison | JPA `@Column(nullable=true)` + `COALESCE` in `@Query` |
| `ISN` column | ADABAS internal sequence number (surrogate key) | JPA `@Id` field or `@GeneratedValue` |
| `ORDER BY ISN` | Preserve ADABAS physical record order | `ORDER BY id ASC` in JPA query |
| `/*+ ALL_ROWS */` | Oracle optimizer hint (full table scan) | Remove — JPA handles this; add `@QueryHints` if needed |
| `NM_SQL_DATE_TO_NAT_DATE()` | Custom Oracle function: SQL DATE → Natural packed date | Replace with `LocalDate` mapping in JPA entity; use `@Temporal` or `AttributeConverter` |
| `RTRIM(:field, CHR(0))` | Remove null byte terminators from COBOL strings | Not needed in Java — String handling is null-byte clean |
| `CLOSE` then `OPEN` cursor | Defensive cursor lifecycle (close before re-open) | JPA manages cursors automatically via connection pool |
| `FOR UPDATE` / `FOR UPDATE NOWAIT` | Row-level locking for UPDATE within FIND loop | JPA `@Lock(LockModeType.PESSIMISTIC_WRITE)` or `@QueryHints` |
| `SESSPAR--WH-ON` conditional | Natural `IN HOLD MODE` — `FOR UPDATE` when true, `FOR UPDATE NOWAIT` when false | Use Spring `@Transactional` with appropriate isolation; JPA handles lock modes |
| `SQLCODE = 100` | End of data / no rows found | JPA: `.findById()` returns `Optional.empty()` / query returns empty list |

#### Work File I/O Patterns (Multi-Output)

Programs often write to **multiple output work files** with **different record structures** per file:

| Work File | Direction | Record Structure | Typical Usage |
|---|---|---|---|
| W01 | INPUT | Field-by-field parsing via `NM--RDWORK` | Input data records |
| W02 | OUTPUT | `STRING record-1 record-2 DELIMITED BY SIZE` | Primary output records |
| W03 | OUTPUT | `STRING record DELIMITED BY SIZE` | Secondary output records |
| W04+ | OUTPUT | `STRING prefix type-indicator record DELIMITED BY SIZE` | Auxiliary output records |

Note: Analyze the actual program to determine which work files are used, their direction, and record layouts.

**Record Assembly Pattern:**
```cobol
MOVE 1 TO NM--WF-LENGTH OF NM--WF-BLOCK
STRING CREFIXE XFRS-VAR DELIMITED BY SIZE
    INTO NM--WF-RECORD OF NM--WF-BLOCK
    WITH POINTER NM--WF-LENGTH OF NM--WF-BLOCK
SUBTRACT 1 FROM NM--WF-LENGTH OF NM--WF-BLOCK
SET NM--WF-OP-WRITE OF NM--WF-BLOCK TO TRUE
MOVE 2 TO NM--WF-NUMBER OF NM--WF-BLOCK
CALL NM--WF-MODULE-PGM USING BY REFERENCE NM--WF-BLOCK
```

**Java migration:** Each work file becomes a separate `Writer`/`ItemWriter`. For output, concatenate DTO serialized bytes:
```java
writer.write(creFixeRecord.toFixedWidth() + fraisVarRecord.toFixedWidth());
```
Note type indicators in records (e.g., `'R'`, `'E'`, `'A'`, `'C'`) — these become a Java enum or constant.
Always analyze the actual STRING statements to identify what record structures are concatenated and what type indicator characters are used.

**⚠️ STRING ... DELIMITED BY SIZE writes the entire structure:**
When the COBOL writes `STRING <structure> DELIMITED BY SIZE INTO NM--WF-RECORD`, the record length equals the **compiled in-memory size** of `<structure>`, not the sum of PIC clauses in the `.cpy` file. If the compiled size differs from the copybook (due to recompilation, REDEFINES overlays, or copybook version mismatch), the actual output will have a different size than expected.

**Always verify:** Compare the theoretical copybook-based record length against actual sample file record lengths BEFORE implementing the serializer. See "Copybook Size Trust-But-Verify Principle" above.

**RDWORK Input Parsing Pattern:**
The `NM--GET-NEXT-RDWORK01` section uses byte-offset parsing:
- `NM--READ-WORK-OFFSET` tracks current position
- `NM--READ-WORK-SIZE = LENGTH OF field` determines bytes to read
- Boundary check: `IF offset + size > buffer-length` truncates read
- Numeric fields: `NM--BYTE-MOVE-PGM` + `IS NOT NUMERIC` validation (raises error 1505)
- Alpha fields: direct `MOVE` from buffer

**Java migration:** Use a `FixedLengthRecordParser` or DTO with field-level deserialization. The field order and sizes define the fixed-width layout.

#### Copybook Size Trust-But-Verify Principle

**CRITICAL LESSON:** The `.cpy` copybook files in the workspace may NOT match the version that was actually compiled into the COBOL binary. This is especially common with large composite structures that are written whole via `STRING ... DELIMITED BY SIZE`.

**Known discrepancy patterns:**
- Copybook field sizes on disk sum to N bytes, but the compiled program's structure is M bytes (M ≠ N)
- Fields may have been added/removed/resized in the `.cpy` after the last COBOL compilation
- Numeric fields that appear as `DISPLAY` in the copybook may have been compiled with a different USAGE
- Group-level REDEFINES may cause the compiler to use the larger overlay size, not the sum of sub-fields

**Mandatory verification protocol:**
1. **Sum all PIC field widths** in the copybook to get the theoretical structure size
2. **Check actual output file record lengths** against this theoretical size
3. If they **match** → proceed with the copybook field widths
4. If they **don't match** → the copybook is UNRELIABLE for that structure:
   - Use the actual file record length as the authoritative size
   - Reverse-engineer field positions from sample data using known anchor values
   - Compare multiple records to identify field boundaries (varying vs constant positions)
   - Request the COBOL compile listing if available
5. **Document ALL discrepancies** in the analysis document and migration report

**Example:** A copybook sums to N bytes, but actual output records are M bytes (M < N). The copybook section order (SECTION-A→SECTION-B→SECTION-C→SECTION-D) may also differ from the actual file order (SECTION-B→SECTION-A+SECTION-D, with SECTION-C absent). Always treat the sample file as the source of truth.

#### Batch Monitoring Pattern (CONTROL / MODSUIVI / ACK-NAK)

Batch programs typically end with execution monitoring calls:

```cobol
*  1) Report statistics via CONTROL sub-program
MOVE SYS-PROGRAM TO XPM-A-PG
MOVE 'NB LUS' TO XPM-A-TX1
MOVE counter TO XPM-A-NN1
MOVE 'CONTROL' TO NM--CALLED-PROGRAM
CALL NM--CALLED-PROGRAM USING BY REFERENCE NM--PARAMETER-BLOCK

*  2) Signal completion via MODSUIVI with ACK/NAK
MOVE 'ACK ' TO XPM-TEST
MOVE ' CORRECT ' TO XPM-VAL
MOVE 'MODSUIVI' TO NM--CALLED-PROGRAM
CALL NM--CALLED-PROGRAM USING BY REFERENCE XPM-VALOUTPUT
```

The **XPM-VALOUTPUT** structure uses an **ACK/NAK pattern**:
```cobol
02  XPM-VALOUTPUT PICTURE X(60).
02  R--XPM-VALOUTPUT REDEFINES XPM-VALOUTPUT.
    03  XPM-TEST PICTURE X(4).   ← 'ACK ' = success, 'NAK ' = failure
    03  XPM-VAL PICTURE X(56).   ← Status description
02  I--XPM-VALOUTPUT.
    03  NM--INITIAL-VALUE PICTURE X(4) VALUE IS 'NAK '.  ← Default = failure (fail-safe)
```

This pattern is always executed inside `IF SYS-DEVICE = 'BATCH'` (batch mode only).

**Java migration:**
- `CONTROL` → logging of execution statistics: `log.info("Program: {} — Records read: {}", programName, count);`
- `MODSUIVI` → Spring Boot exit code: `return new ExitCodeGenerator(() -> 0)` for ACK, non-zero for NAK
- `XPM-VALOUTPUT` → no Java equivalent needed; replace with structured logging and proper exit codes
- The `SYS-DEVICE = 'BATCH'` check is always true in batch migration — remove the conditional

#### File Fusion/Merge Pattern (Multi-Input Merge)

Programs that merge multiple sorted input files use a **fusion algorithm** pattern:

```cobol
*  Two fusion structures with composite sort keys
02  XWK-FUSION-1 PICTURE X(41).
02  R--XWK-FUSION-1 REDEFINES XWK-FUSION-1.
    03  XWK-FIN-FICH-1 PICTURE S9(1).    ← End-of-file flag (0=more, 1=EOF)
    03  XWK-CLE-COMP-1 PICTURE X(39).    ← Composite sort key
    03  XWK-NUM-FICH-1 PICTURE S9(1).    ← Source file indicator (1 or 2)

*  SP-FUSION subroutine: swap to keep smallest key "left"
IF XWK-FUSION-1 > XWK-FUSION-2 THEN
    MOVE XWK-FUSION-1 TO XWK-FUSION-X
    MOVE XWK-FUSION-2 TO XWK-FUSION-1
    MOVE XWK-FUSION-X TO XWK-FUSION-2
END-IF
```

The main loop then processes three cases:
1. **Keys equal** (record in both files) → merge/join processing
2. **Key only in file 1** → file-1-only processing
3. **Key only in file 2** → file-2-only processing

**Java migration:** Use a **merge-join algorithm** with two `Iterator`s or `BufferedReader`s:
```java
while (hasMore1 || hasMore2) {
    int cmp = key1.compareTo(key2);
    if (cmp == 0) { processBothFiles(rec1, rec2); advance both; }
    else if (cmp < 0) { processFile1Only(rec1); advance reader1; }
    else { processFile2Only(rec2); advance reader2; }
}
```

### Job Orchestration Layer (UC4 / Perl Scripts — CRITICAL)

**WHY THIS MATTERS:** Anubex-migrated COBOL programs do NOT run in isolation. Each COBOL program is ONE step in a multi-step batch job orchestrated by UC4 parent jobs (`lib.uc4/*.pl`) and sub-procedure scripts (`lib.do/*.pl`). These scripts perform **critical pre-processing and post-processing** that is NOT contained in the COBOL source code. Migrating ONLY the COBOL program without its surrounding orchestration produces an **incomplete and non-functional** Java application.

#### Orchestration Architecture

```
UC4 Parent Job (lib.uc4/{job}.pl)
├── Step 010: Sub-procedure (lib.do/{step1}.pl) — e.g., SORT, FILE-COPY, EOFV
├── Step 020: Sub-procedure (lib.do/{step2}.pl) — e.g., SORT pre-processing
├── Step 030: Sub-procedure (lib.do/{step3}.pl) — e.g., COBOL program execution
├── Step 040: Sub-procedure (lib.do/{step4}.pl) — e.g., SORT post-processing
└── Step 050: Sub-procedure (lib.do/{step5}.pl) — e.g., Report printing
```

Each UC4 parent job defines the **execution sequence**, **error handling** (ERREUR jump), and **restart capability** (SUIVI step tracking). Sub-procedures are the actual work units.

#### Sub-Procedure Script Classifications

Every `lib.do/*.pl` script falls into one of these categories:

| Classification | Description | Java Migration Target |
|---|---|---|
| **SORT** | BS2000 SORT utility — sorts a file by specified key positions | `FileOperationsService.sortByKey()` from `gesfac-tva-common` — called in the batch module's runner as a pre/post-processing step |
| **COBOL** | Runs a COBOL program (Natural batch via `EXEC {PROGRAM}`) | The main `{Program}Migration` Spring Boot module — **this is what the existing agent phases cover** |
| **PERCON** | BS2000 PERCON utility — concatenates multiple input files into one output file | `FileOperationsService.concatenateFiles()` from `gesfac-tva-common` — reads all input files sequentially, writes combined output |
| **FILE-COPY** | Copies a file (backup/retention) — `COPY-FILE FROM-FILE=X TO-FILE=Y` | `FileOperationsService.copyFile()` from `gesfac-tva-common` — backup/retention copy |
| **EOFV** | Truncates/empties a file — `EOFV` utility | `FileOperationsService.truncateFile()` from `gesfac-tva-common` — file initialization before writes |
| **FTP** | File transfer between systems | Out of scope for batch migration — document as external dependency |
| **REPORT-PRINT** | Formats and prints report output (PCL.FORMAT, DP.FORMAT) | Log output or file output — integrate into COBOL program's report writer |
| **UNESCAPE** | Post-processing: `UNESCAPE.LINE-SEQUENTIAL.IN-PLACE` on output files | Character encoding cleanup — may not be needed in Java (UTF-8 native) |

**IMPORTANT — Shared `FileOperationsService` (Category A → `gesfac-tva-common`):**

ALL file operations from Perl DO scripts MUST use the **shared** `FileOperationsService` from `gesfac-tva-common`. Do NOT create module-local `FileSortService`, `FileConcatenationService`, or similar classes in individual batch modules.

**Location:** `gesfac-tva-common/src/main/java/com/sgcib/gesfac/tva/common/service/FileOperationsService.java`

| Method | DO Script Operation | Parameters |
|---|---|---|
| `sortByKey(input, output, position, length)` | BS2000 SORT | 0-based position (convert from BS2000 1-based), ascending by default |
| `sortByKey(input, output, position, length, ascending)` | BS2000 SORT | Explicit sort direction (true=ASC, false=DESC) |
| `concatenateFiles(List<inputs>, output)` | BS2000 PERCON | Sequential concatenation, skips missing files with warning |
| `truncateFile(path)` | EOFV | Creates parent dirs, empties file (or creates if not exists) |
| `copyFile(source, target)` | FILE-COPY | Line-by-line copy preserving charset, creates target dirs |

All methods use `ISO_8859_1` charset (COBOL standard). Inject via constructor:
```java
private final FileOperationsService fileOps;
public MyRunner(FileOperationsService fileOps) { this.fileOps = fileOps; }
```

#### SORT Script Pattern (BS2000 → Java)

SORT scripts use the BS2000 SORT utility with specific key definitions:

```perl
# BS2000 SORT inline parameters (from lib.do script)
bs2k_inline_sysdta("SORT FIELDS(707,25,CH,A,1723,21,CH,A),FORMAT=*VARIABLE,BUFFER=16");
```

Key format: `SORT FIELDS(POS,LEN,TYPE,ORDER, ...)` where:
- `POS` = 1-based byte position in the record
- `LEN` = field length in bytes
- `TYPE` = `CH` (character), `BI` (binary), `ZD` (zoned decimal)
- `ORDER` = `A` (ascending), `D` (descending)

**Java migration — use `FileOperationsService` from `gesfac-tva-common`:**
```java
// Convert BS2000 1-based positions to Java 0-based, then call shared service
// BS2000: SORT FIELDS(707,25,CH,A) → Java: position=706, length=25
fileOps.sortByKey(inputPath, outputPath, 706, 25);  // single key, ascending

// For multi-key sorts, chain with .thenComparing in a custom Comparator
// passed to a local sort helper, or call sortByKey for the primary key
```

**CRITICAL:** The sort key positions in the Perl scripts are **1-based** (BS2000 convention). `FileOperationsService.sortByKey()` expects **0-based** positions. Always subtract 1 when converting.

#### PERCON Script Pattern (File Concatenation → Java)

PERCON concatenates multiple input files into a single output file sequentially:

```perl
# BS2000 PERCON with multiple inputs
bs2k_set_file_link('IN1', "$disk F.INPUT.FILE1", ...);
bs2k_set_file_link('IN2', "$disk F.INPUT.FILE2", ...);
bs2k_set_file_link('OUT', "$disk F.OUTPUT.COMBINED", ...);
# IN1 records come first, then IN2 records, etc.
```

**Java migration — use `FileOperationsService` from `gesfac-tva-common`:**
```java
// Concatenate multiple input files into a single output
List<String> inputs = List.of(inputPath1, inputPath2, inputPath3);
long totalRecords = fileOps.concatenateFiles(inputs, outputPath);
// Missing input files are skipped with a warning (handles *DUMMY links)
```

**Note:** PERCON with `*DUMMY` input links means "skip this input" — it's a placeholder for optional file sources. `FileOperationsService.concatenateFiles()` handles this by skipping non-existent files with a warning log.

#### EOFV + FILE-COPY Patterns (File Initialization → Java)

These are pre-processing operations that prepare the file system before COBOL execution. Use `FileOperationsService` from `gesfac-tva-common`:

```java
// EOFV — truncate/initialize output file (ensure it's empty before writes)
fileOps.truncateFile(outputPath);

// FILE-COPY — backup before overwrite (retention/veille pattern)
fileOps.copyFile(retentionPath, retentionVeillePath);
```

#### UC4 Step Sequencing → Java Runner Integration

The UC4 parent job defines the execution order. In Java, ALL steps from the UC4 job must be integrated into the Spring Boot `CommandLineRunner.run()` method, using the **shared `FileOperationsService`** from `gesfac-tva-common`:

```java
private final FileOperationsService fileOps;  // Injected from gesfac-tva-common

@Override
public void run(String... args) throws Exception {
    // *** PRE-PROCESSING: Steps from UC4 sub-procedures before COBOL ***
    // Step 010 (lib.do script): e.g., FILE-COPY backup
    fileOps.copyFile(retentionPath, veillePath);
    // Step 020 (lib.do script): e.g., SORT input file (BS2000 POS → 0-based)
    fileOps.sortByKey(rawInputPath, sortedInputPath, keyPosition, keyLength);
    // Step 025 (lib.do script): e.g., EOFV truncate output before writes
    fileOps.truncateFile(outputPath);

    // *** MAIN PROCESSING: COBOL program logic (from .cbl analysis) ***
    initializeEntity();
    processFiles();

    // *** POST-PROCESSING: Steps from UC4 sub-procedures after COBOL ***
    // Step 040 (lib.do script): e.g., SORT output for next job
    fileOps.sortByKey(primaryOutput, sortedOutput, postSortPosition, postSortLength);
    // Step 050 (lib.do script): e.g., Report formatting
    logStatistics();
}
```

##### Buffer Copy Width vs Format Width (CRITICAL Pattern)

COBOL programs frequently use this pattern to place formatted data into output lines:

```cobol
*  Format the number into 151-byte buffer (pre-initialized to spaces)
CALL NM--EDIT-PGM USING BY REFERENCE field, ..., XWK-LIG-AVIS, BY VALUE 151
*  Copy field-length chars from buffer into output line
PERFORM VARYING idx FROM 1 BY 1 UNTIL idx > XWK-LNG
    COMPUTE target-pos = idx - 1 + XWK-DEB
    MOVE XWK-LIG-AVIS-TAB(idx) TO output-line(line, target-pos)
END-PERFORM
```

The copy loop copies `XWK-LNG` characters (= `XTAB-FORM-LNG` from TB266), but the formatted result from `NM--EDIT-PGM` may be SHORTER than `XWK-LNG`. The extra characters are **spaces from buffer initialization**, not part of the formatted value.

Example: For a numeric field with TB266 `XTAB-FORM-LNG = 20` and decimal `NM--EDIT-PGM` output of 18 chars:
- Buffer positions 1-18: formatted number (right-justified with leading-zero suppression)
- Buffer positions 19-20: spaces (from `INITIALIZE XWK-LIG-AVIS`)
- Copy loop copies all 20 chars → output gets 18-char number + 2 trailing spaces

**Java migration:** The Java formatter should produce the **edit mask output width** (e.g., 18 chars), NOT the field width from TB266. The `writeToLine` method naturally handles the difference:
- It writes only `min(formattedString.length, fieldLength)` chars
- The output line is pre-initialized to spaces, so positions beyond the formatted string remain as spaces
- This matches the COBOL behavior exactly

```java
// CORRECT: format to edit mask width (18), let writeToLine handle field width (20)
String formatted = NumberFormatter.format(rawValue, decimals); // returns 18-char string
ctx.writeToLine(line, startPos, formatted, fieldLength);       // fieldLength=20, writes 18 chars, 2 trailing spaces remain

// WRONG: format to field width (20) — shifts number right by 2 positions
String formatted = NumberFormatter.format(rawValue, decimals, fieldLength); // returns 20-char string — TOO WIDE
```

**Rule:** When the COBOL chain is `NM--EDIT-PGM` → buffer → copy loop with `XWK-LNG`, always use the **edit output width** for the Java formatter, NOT the `XWK-LNG`/`XTAB-FORM-LNG` field length.

**Early Output Comparison (MANDATORY during Phase 3):**

Do NOT wait until Phase 5 to compare output. As soon as the first complete output unit (record, notice, line group) can be generated, perform a byte-level comparison against the expected reference:

1. **Build and run** with a minimal input subset (or the full input if fast enough)
2. **Compare at least 2-3 output records/notices** at the byte level against the expected reference file
3. **Check both alpha AND numeric fields** — formatting, positioning, and padding issues manifest differently in each type
4. **Check ALL record types** — headers, data records, summary lines, control records. If any record type is blank or missing content, investigate immediately
5. **Fix issues immediately** — catching a formatting or positioning bug during implementation is 10x cheaper than debugging it in Phase 5 with 1000+ diff lines

- **Numeric format width errors** — only visible when comparing exact byte positions (e.g., shift-by-1 from edit mask width miscount)
- **Record-type processing gaps** — only visible when checking ALL record types (e.g., header enrichment skipped)
- **Buffer copy vs format width confusion** — only visible when formatted values are compared at their target positions

##### Phase 4 Sub-Step: Tracing a Diff to Root Cause (Methodology)

When a byte-level comparison reveals a difference, follow this systematic trace-back:

1. **Identify the field:** Use the serializer's offset map to determine which DTO field occupies the differing byte position
2. **Check the serializer:** Is the field being formatted correctly? (e.g., `pad()` vs `zonedDecimal()`, correct width, correct alignment)
3. **Check the DTO population:** Where is this field set in the Java service? Is the value correct before serialization?
4. **Check the source:** Trace the value back to its origin — DB query, input file parse, computation, or sub-program result
5. **Compare with COBOL:** Read the exact COBOL lines that produce this field. Check for:
   - Reference modification offsets (`field(41:2)` = Java `substring(40, 42)`)
   - REDEFINES overlays that change field interpretation
   - COMPRESS behavior (trailing space trimming)
   - Zoned decimal formatting vs alphanumeric padding
   - Separator characters in REDEFINES structures (e.g., `CODE-LIB(3) + SEP(1) + LIB-ABRV(15)`)
6. **Fix and re-verify:** After fixing, rebuild and compare ALL output files — a single root cause often affects multiple outputs

##### Phase 4 Sub-Step: Common Root Cause Categories

| Symptom | Root Cause | Example |
|---|---|---|
| Field value shifted by 1 byte | Separator field in REDEFINES not accounted for | `CODE-LIB(3)+SEP(1)+LIB-ABRV(15)` → skip offset 3, extract from offset 4 |
| Numeric field shows wrong value | COBOL reference modification offset wrong | `TFI-VAL(1)(41:2)` → Java `substring(40, 42)` not `substring(0, 3)` |
| 1-byte field has wrong value | REDEFINES alias used instead of actual field | `ENT-JUR REDEFINES CDREGL(1:1)` → extract first byte of CDREGL |
| Numeric field format wrong | Zoned decimal via alpha REDEFINES | S9(4)V9(7) needs `zonedDecimal()` not `pad(toPlainString())` |
| Lookup returns wrong data | Compound key COMPRESS trims trailing spaces | TYCRS key: `COMPRESS field1 field2 INTO key` trims spaces |
| Sub-program returns wrong result | Multi-field extraction from F_TABLES value | `TFI-VAL` holds composite data; must extract at correct offsets |

### Core Principles (apply at ALL phases)

1. **Analysis Before Code**: NEVER generate Java without completing functional analysis first. The analysis catches edge cases, nested call chains, and business rules that ad-hoc migration misses.

2. **Strip Anubex Scaffolding**: Focus only on `NM--USER-CODE` sections for business logic. All `NM--` lifecycle code is framework overhead to be removed.

3. **Preserve Exact Behavior**:
   - Output file formats must be byte-identical
   - Monetary calculations use `BigDecimal` only (NEVER `float`/`double`)
   - Business rules (EVALUATE/DECIDE) must be exact
   - Error messages stay in original French

4. **Modern Java Standards**:
   - Java 21 with records, pattern matching, sealed classes
   - Spring Boot 3.x conventions
   - JPA for database access
   - SLF4J + `@Slf4j` for logging
   - Proper exception handling (no GO TO)

5. **Trace Every Sub-Program**: NEVER skip a CALLNAT — recursively analyze every called program

6. **Show Evidence**: Quote actual COBOL lines that support each finding; reference line numbers in analysis

7. **Preserve Domain Terms**: Use original French/domain terms with English translations in parentheses

8. **Document REDEFINES**: Always show both original and redefined views — they reveal data interpretation

9. **Note All Hardcoded Values**: Constants, magic numbers, entity codes, table names embedded in logic

10. **Track Data Lineage**: For key output fields, trace backwards through all transformations to original input

11. **Verify Against Sample Data**: NEVER trust copybook field sizes alone. Always validate serializer/parser record lengths against actual sample data files before finalizing the implementation. The `.cpy` file in the workspace may not match the compiled COBOL binary. When a mismatch is found, the sample data is the **authoritative source of truth** — reverse-engineer the structure from the data, not the copybook.

12. **Anchor-Based Field Mapping**: When record structures don't match copybooks, use known field values as anchors (e.g., search for application names, person IDs, distinctive dates/codes in the output) and map field boundaries outward from these anchor points.

13. **Migrate the Complete Job, Not Just the COBOL**: A COBOL program is ONE step in a UC4 batch job. The job orchestration scripts (`lib.uc4/` parent jobs, `lib.do/` sub-procedures) define SORT, PERCON (file concatenation), FILE-COPY, and EOFV (file truncation) steps that MUST be integrated into the Java application. Without these, the migrated program is incomplete and may produce incorrect results (e.g., unsorted input to a merge-join).

14. **Orchestration Steps Are First-Class Citizens**: SORT, PERCON, FILE-COPY, and EOFV steps from `lib.do/` scripts are NOT optional boilerplate — they implement critical data preparation logic. Treat them with the same rigor as COBOL business logic: analyze, design, implement, validate.

- Do NOT translate `NM--` framework code to Java — it's scaffolding, not business logic

- Do NOT simplify business rules — preserve exact EVALUATE/IF logic
- Do NOT skip error handling from `NM--NO-RECORDS-FOUND` sections — these contain critical fallback logic
- Do NOT guess when a copybook or sub-program cannot be found — explicitly state it is missing
- Do NOT start coding without completing the functional analysis document
- Do NOT skip sub-programs in the call chain — incomplete analysis leads to broken migration
- Do NOT create a Java "parameter block" byte buffer — convert `PB--` REDEFINES to typed method parameters
- Do NOT keep meaningless `H--` variable names — rename ALL helper variables to descriptive names
- Do NOT use `switch` for `EVALUATE TRUE` with range conditions — use `if-else if` chains
- Do NOT forget 1-based to 0-based index conversion for `field(start:length)` → `substring(start-1, ...)`

- Do NOT implement fusion/merge with random access — use sorted merge-join with iterators
- Do NOT create a separate Maven module per shared sub-program — consolidate ALL shared services into `gesfac-tva-common`
- Do NOT duplicate a sub-program's service in a batch module if it already exists in `gesfac-tva-common` — add the dependency and inject it
- Do NOT place shared entities/repositories in individual batch modules — if a table is accessed by shared services, the entity and repository belong in `gesfac-tva-common`
- Do NOT forget `@ComponentScan`, `@EntityScan`, `@EnableJpaRepositories` annotations on the batch module's `@SpringBootApplication` when depending on `gesfac-tva-common`
- Do NOT trust copybook PIC field sizes as the sole source for serializer/parser widths — always validate against sample data; the `.cpy` on disk may differ from the compiled COBOL binary
- Do NOT finalize a FixedWidthSerializer without running a byte-level verification against actual COBOL output sample files
- Do NOT assume the field order in a `.cpy` copybook matches the order written to a work file — the COBOL `STRING` statement determines the actual concatenation order
- Do NOT assume all sections of a composite copybook structure are written — some sections may be excluded or empty in specific work file outputs
- Do NOT use `String.split()` to parse F_TABLES TFI_VAL — always use fixed-offset extraction per REDEFINES layout
- Do NOT skip separator characters in REDEFINES structures — a field after `SEP PIC X(1)` starts at offset+1, not at the separator position
- Do NOT use `BigDecimal.toPlainString()` or `pad()` for fields that go through alpha REDEFINES of S9(m)V9(n) — use `zonedDecimal()` format
- Do NOT assume a variable named `DEV1` contains a currency code — trace the actual MOVE chain to verify what data populates each field used in COMPRESS key construction
- Do NOT use simple `String.format("%-Xs", field)` for COMPRESS-based keys — must `trim()` each component first, then concatenate, then pad to target width
- Do NOT assume COBOL field names in REDEFINES aliases match the business semantics — `ENT-JUR REDEFINES CDREGL(1:1)` may NOT be the same `ENT-JUR` used elsewhere
- Do NOT skip the position-to-field mapping before output comparison — without it, diff positions are meaningless numbers
- Do NOT batch multiple fix categories in a single rebuild — fix one category at a time and re-compare ALL output files after each fix

- Do NOT assume the character count of an edit mask string equals the NM--EDIT-PGM output width — the decimal comma is embedded WITHIN the base width, not added to it (e.g., `ZZZZZZZZZZZZZZZZ9,99` = 19 mask chars but **18-char output**)

- Do NOT migrate a COBOL program WITHOUT analyzing its UC4 parent job orchestration (`lib.uc4/` + `lib.do/`) — SORT, PERCON, FILE-COPY, and EOFV steps are NOT in the COBOL code but are critical to correct execution
- Do NOT assume a COBOL program runs standalone — it is always ONE step in a multi-step UC4 job; the pre/post-processing steps MUST be integrated into the Java runner

- Do NOT skip backup/FILE-COPY steps — they implement retention mechanisms (veille/jour pattern) that are essential for day-over-day processing recovery

### Lessons Learned — Real Pitfalls from Migration (MUST READ)

These are actual bugs encountered during the TVABNFRQ migration that took significant debugging effort. **Every one of these will recur in future migrations** unless explicitly checked.

#### Pitfall 1: Separator Fields in REDEFINES (libAbrv `/` bug)

**Symptom:** Output field starts with an unexpected `/` character.

**Root Cause:** The COBOL REDEFINES of a table value has a **separator field** between sub-fields:
```cobol
02  R--TFI-VAL REDEFINES TFI-VAL.
    03  CODE-LIB    PICTURE X(3).    ← offset 0–2
    03  SEP         PICTURE X(1).    ← offset 3 (separator '/', NOT part of output!)
    03  LIB-ABRV    PICTURE X(15).   ← offset 4–18
```
The Java code used `val.substring(3)` which included the separator. Correct: `val.substring(4, 19)`.

**Rule:** When parsing REDEFINES of F_TABLES.TFI_VAL, always check for separator fields (typically `/`, `*`, `-`). The sub-field you want is AFTER the separator, not starting at the separator position.

#### Pitfall 2: COBOL 1-Based Reference Modification (devAnc `99` vs `93` bug)

**Symptom:** A 2-character code field returns `99` instead of `93`.

**Root Cause:** COBOL uses `TFI-VAL(1)(41:2)` which means: starting at byte 41 (1-based), take 2 bytes. Java must translate to `val.substring(40, 42)` (0-based). The Java code incorrectly used `val.substring(0, 3)` extracting a completely different part of the value.

**Rule:** EVERY `field(start:length)` reference modification must be translated as:
```java
field.substring(start - 1, start - 1 + length)
```
Always verify the offset is decremented by 1 for Java's 0-based indexing.

#### Pitfall 3: REDEFINES Alias vs Actual Field (ENT-JUR bug)

**Symptom:** A 1-byte field shows `61` instead of the expected `1 ` (with trailing space).

**Root Cause:** The COBOL copies `ENT-JUR OF CREFIXE` which is a 1-byte REDEFINES of the first byte of `CDREGL`:
```cobol
02  CDREGL    PICTURE X(2).       ← "61"
02  R--CDREGL REDEFINES CDREGL.
    03  ENT-JUR PICTURE X(1).     ← "6" (first byte only — NOT what we want!)
```
But the actual business field being written is `ENT-JUR` from a DIFFERENT context (the parameter block), where it's a 2-byte field containing `"1 "`. The Java code was using the full `idtEntJur` (2 bytes) instead of extracting just `cdRegl.substring(0, 1)`.

**Rule:** When a field name appears in multiple REDEFINES contexts, trace the EXACT copybook and EXACT COBOL MOVE statement to determine which definition is being used. Never assume the most obvious definition is the right one.

#### Pitfall 4: Zoned Decimal via Alpha REDEFINES (CRS-BASE formatting bug)

**Symptom:** A numeric field shows `0012.3400000` instead of `+00123400000`.

**Root Cause:** The COBOL field is:
```cobol
02  CRS-BASE    PICTURE X(11).          ← Alpha overlay
02  R--CRS-BASE REDEFINES CRS-BASE.
    03  filler   PICTURE S9(4)V9(7).    ← Zoned decimal format
```
When written via `STRING ... DELIMITED BY SIZE`, the **zoned decimal format** is used (sign + digits, no decimal point). The Java code used `pad(value.toPlainString(), 11)` which produces `0012.3400000` instead of the correct `+00123400000`.

**Rule:** When a PIC X(n) field is REDEFINES'd as S9(m)V9(p), the output format is **zoned decimal** (total m+p+1 digits including sign), NOT a formatted decimal string. Use a `zonedDecimal(value, intDigits, decDigits)` formatter.

#### Pitfall 5: Natural COMPRESS Trimming in Key Construction

**Symptom:** Database lookup returns no results or wrong results.

**Root Cause:** Natural's `COMPRESS field1 field2 INTO key` **trims trailing spaces** from each field before concatenation, then pads the result. The key `"EUR   " + "TXCH  "` becomes `"EUR" + "TXCH" = "EURTXCH     "` (trimmed, then padded to key length), NOT `"EUR   TXCH  "` (simple concatenation).

If Java uses `String.format("%-6s%-6s", "EUR", "TXCH")` → `"EUR   TXCH  "` → lookup FAILS.
Correct: `("EUR".trim() + "TXCH".trim())` padded to required length → `"EURTXCH     "` → lookup SUCCEEDS.

**Rule:** EVERY `COMPRESS` used for key construction must be translated as: trim each component, concatenate trimmed values, then pad the result to the target field width. Check ALL COMPRESS results used in EXEC SQL WHERE clauses or FIND conditions.

#### Pitfall 6: F_TABLES Multi-Field Value Extraction

**Symptom:** Multiple fields extracted from the same TFI_VAL return wrong values.

**Root Cause:** `F_TABLES.TFI_VAL` is a variable-purpose text column. Each table code (TFI_CDTFI) has a different REDEFINES layout for TFI_VAL. When a sub-program enriches a DTO, it may need 3-5 different fields from a single TFI_VAL, each at different offsets.

Example: Currency info from a single TFI_VAL (size 60):
```
Offset  0-2:   Currency code (3 chars)
Offset  3:     Separator
Offset  4-18:  Short label (15 chars)
Offset 40-41:  Former currency code (2 chars)
Offset 43:     Decimal position (1 char)
Offset 44:     Status (1 char)
Offset 45:     Quotation mode (1 char)
```

**Rule:** Always extract ALL fields from TFI_VAL at their correct REDEFINES offsets. Build a field-offset map from the copybook and validate against sample data. Never assume fields are contiguous — there may be gaps, fillers, or unused regions.

#### Pitfall 7: TYCRS Compound Key with COMPRESS

**Symptom:** Exchange rate lookup fails — no matching TYCRS record found.

**Root Cause:** The TYCRS lookup key is built with COMPRESS:
```cobol
COMPRESS DEV1 TYCRS INTO MEC OF EURCV1
```
Where DEV1 is the **category code** (e.g., `"TXCH"`), not the currency code. The Java code used the wrong field (currency code instead of category code), producing a key like `"EURTXCH "` instead of `"TXCHTXCH"`.

**Rule:** When migrating COMPRESS-based key construction, trace EVERY field to its actual source. Don't assume variable names indicate content — `DEV1` might not be a currency code. Read the COBOL MOVE statements that populate the field before the COMPRESS.

#### Pitfall 8: Oracle Connection Timeout on First Run

**Symptom:** Application hangs at startup, no error message.

**Root Cause:** Spring Boot's default HikariCP connection timeout may be too long, or Oracle listener is slow. Without explicit timeout configuration, the application appears to hang.

**Rule:** Always configure explicit connection timeouts in `application.yml`:
```yaml
spring:
  datasource:
    hikari:
      connection-timeout: 30000
      maximum-pool-size: 5
      login-timeout: 10
```

#### Pitfall 9: Work File Name Mismatch

**Symptom:** `FileNotFoundException` at runtime.

**Root Cause:** The COBOL work file names (configured via SESSPAR or JCL) don't match the paths in `application.yml`. Work file numbers (W01, W02, W03...) may map to different actual file names than expected.

**Rule:** Cross-reference the COBOL JCL or SESSPAR configuration with the `application.yml` work file paths. Verify every file exists at the configured path before running.

#### Pitfall 10: JAVA_HOME Not Set Between Sessions

**Symptom:** Build fails with `invalid target release: 21` or `JAVA_HOME not set`.

**Root Cause:** `$env:JAVA_HOME` in PowerShell is session-scoped. Every new terminal window loses it.

**Rule:** Set `$env:JAVA_HOME` as the FIRST command in every new terminal session before any Maven or Java command.

#### Pitfall 11: NM--EDIT-PGM Output Width ≠ Edit Mask String Length (Decimal Shift Bug)

**Symptom:** All decimal numeric values are shifted right by 1 position in the output (e.g., `25,00` appears at column 76 instead of column 75).

**Root Cause:** The COBOL edit mask for decimals (e.g., `ZZZZZZZZZZZZZZZ9,99`) has 19 characters, so the Java formatter was set to produce 19-character output. But `NM--EDIT-PGM` actually produces **18-character output** for ALL numeric masks — the comma replaces one digit position within the 18-char layout, it does NOT add an extra character. The 18 is the output width, confirmed by examining the `NM--EDIT-PGM` call parameters:

```cobol
*  Integer (dec=0): mask = 18 chars, output = 18 chars
CALL NM--EDIT-PGM USING BY REFERENCE field, BY VALUE 18,
  BY CONTENT '(N18)', BY VALUE 5,
  BY CONTENT 'ZZZZZZZZZZZZZZZZZ9', BY VALUE 18,
  BY REFERENCE buffer, BY VALUE 151

*  Decimal (dec=2): mask = 19 chars, but output still = 18 chars!
CALL NM--EDIT-PGM USING BY REFERENCE field, BY VALUE 12,
  BY CONTENT '(P15.7)', BY VALUE 7,
  BY CONTENT 'ZZZZZZZZZZZZZZZ9,99', BY VALUE 19,
  BY REFERENCE buffer, BY VALUE 151
```

The input for decimals is `XWK-COMM-VAL-NUM PIC S9(15)V9(7) PACKED-DECIMAL` (12 bytes), which after DIVIDE scaling produces the correct value. The edit result occupies 18 display characters (15 integer Z/9 positions + comma + 2 decimal 9 positions = 18 visual slots). The 19 passed as mask-length describes the mask string itself, not the output.

**Rule:** ALWAYS format numeric output to **18 characters** regardless of decimal count. Never derive the formatter width from the edit mask string length or from TB266 `XTAB-FORM-LNG`.

#### Pitfall 12: Buffer Copy Width ≠ Format Output Width (Field Width Overcorrection)

**Symptom:** After fixing the decimal shift, attempt to use TB266's `XTAB-FORM-LNG` (e.g., 20) as the formatter width causes integers to shift by 2 positions.

**Root Cause:** COBOL copies `XWK-LNG` (= `XTAB-FORM-LNG` = 20) bytes from a 151-byte buffer into the output line. The buffer is pre-initialized to spaces. `NM--EDIT-PGM` writes its 18-char result starting at position 1 of the buffer. Positions 19-20 remain as spaces. The copy loop then copies all 20 bytes: 18-char formatted number + 2 trailing spaces.

If the Java formatter pads the result to 20 characters (the field width), it produces `"                  1"` (20 chars, right-justified) instead of `"                 1"` (18 chars) + 2 separate trailing spaces. This shifts the visible number 2 positions to the right.

**Rule:** The Java formatter should produce the **edit mask output width** (18 chars), not the field width. The `writeToLine` method writes only `min(formatted.length, fieldLength)` characters; the remaining field positions stay as pre-initialized spaces, naturally matching COBOL behavior.

#### Pitfall 13: Processing Path Assumptions for Record Types (Header Enrichment Bug)

**Symptom:** Header/control lines in output are blank where they should contain formatted data (e.g., `*`-prefixed control records in notice headers).

**Root Cause:** The Java migration added a record-type guard (`if (!record.isHeader()) { enrichRecord(...) }`) assuming header/control records are structural-only and don't need enrichment. But the COBOL processes ALL records (including HEAD) through the same enrichment loop:

```cobol
*  COBOL: No record-type guard — ALL records go through enrichment
PERFORM NM--FOR04-TVABNAVI    ← enrichment loop, runs for EVERY record
```

The HEAD record's enrichment is triggered because its CODE-CHMP ('HEAD') matches a TB266 format field of type 'A' at position 1 with length 150, which places the `*`-prefixed control data into the first notice line.

**Rule:** NEVER add Java record-type guards to skip processing unless the COBOL **explicitly** branches on record type (e.g., `IF record-type = 'HEAD' THEN ... ELSE ...`). If the COBOL loop processes all records uniformly, the Java must do the same. Always verify the COBOL processing path for each record type rather than assuming what records "should" or "shouldn't" need processing.

#### Pitfall 14: Missing Job Orchestration — SORT/PERCON/EOFV Steps Not Migrated

**Symptom:** Java application runs the COBOL logic correctly but the merge-join fails or produces wrong results because input files are not sorted. Or output files contain stale data from previous runs.

**Root Cause:** The COBOL program was migrated in isolation, without analyzing the UC4 parent job (`lib.uc4/`) and its sub-procedure scripts (`lib.do/`). The parent job defines critical pre-processing steps (SORT, FILE-COPY, EOFV) and post-processing steps (SORT, REPORT) that are NOT in the COBOL source code. These steps were executed by the BS2000 operating system _before_ the COBOL program ran.

**Example from TVAEQCOM:**
- Step 010 (tvadqco1.pl): SORT `F.TV12.REPONSE.TVA` → `W.TV214.REQ.TRI` (by PST+IDPSTFRAI)
- Step 020 (tvadqco2.pl): SORT `F.TV21.PRST` → `W.TV214.PST.TRI` (by PST+IDPSTFRAI)
- Step 030 (tvadqcom.pl): Run COBOL `TVABNCOM` (merge-join on sorted files)

Without Steps 010+020, the COBOL merge-join receives unsorted files and produces garbage.

**Rule:** ALWAYS analyze the UC4 parent job and ALL its sub-procedure scripts BEFORE migrating the COBOL program. Integrate every SORT, PERCON, FILE-COPY, and EOFV step into the Java `CommandLineRunner.run()` method in the correct order.

#### Pitfall 15: BS2000 SORT Key Position Off-By-One

**Symptom:** Sort produces wrong order; records with similar prefixes sort incorrectly.

**Root Cause:** BS2000 SORT key positions are **1-based** (`POS=707` means starting at byte 707, counting from 1). Java `String.substring()` is **0-based**. The Perl scripts pass raw BS2000 positions. If the Java sort service uses these directly without subtracting 1, the sort key starts one byte too late.

**Rule:** EVERY sort key position from a `lib.do/*.pl` script must be decremented by 1 for Java. Store the **0-based** position in `application.yml` with a comment showing the original BS2000 value:
```yaml
sort:
  response:
    pst-position: 706    # BS2000 POS=707 → 0-based 706
```

## Example Interactions

### Example 1: Full Migration (first TVA program)

**User**: Migrate {program}.cbl to Java

**Agent** (follows all 5 phases):
1. **Phase 1 — Analysis**: Searches `lib.uc4/` and `lib.do/` to find the UC4 parent job and all orchestration steps. Reads the full COBOL program, traces all CALLNAT sub-programs recursively, documents all DB tables and work files, extracts all business rules. Classifies each sub-program as Category A/B/C. Documents all SORT/PERCON/EOFV/FILE-COPY steps. Produces a structured analysis document.
2. **Phase 2 — Design**: Maps analysis to JPA entities, DTOs, services, I/O classes, and enums. Category A sub-programs → `gesfac-tva-common`. Category B/C → batch module. Uses shared `FileOperationsService` from `gesfac-tva-common` for all orchestration steps (SORT, PERCON, EOFV, FILE-COPY).
3. **Phase 3 — Implementation**: Reuses `FileOperationsService` from `gesfac-tva-common` (already exists). Creates batch module with COBOL program logic AND all orchestration steps called via `fileOps.sortByKey()`, `fileOps.truncateFile()`, etc. in the runner.
4. **Phase 4 — Validation**: Checklist verification of output formats, business rules, type safety. Verifies all UC4 steps are covered.
5. **Phase 5 — Delivery**: Provides parent POM, module POMs, application.yml, migration report, test guidance.

### Example 2: Subsequent TVA Program Migration

**User**: Migrate {another-program}.cbl to Java

**Agent** (reuses existing common module):
1. **Phase 1 — Analysis**: Same recursive analysis. For each CALLNAT sub-program, checks if it already exists in `gesfac-tva-common`. Identifies all Perl DO script operations (SORT, PERCON, EOFV, FILE-COPY).
2. **Phase 2 — Design**: Already-migrated sub-programs → reuse from `gesfac-tva-common` (just inject). New shared sub-programs → add to `gesfac-tva-common`. Program-specific → batch module. **File operations** → reuse `FileOperationsService` from `gesfac-tva-common` (already exists).
3. **Phase 3 — Implementation**: Creates new batch module `{program}-migration/`. Injects `FileOperationsService` for all SORT/PERCON/EOFV/FILE-COPY operations — no new file operation classes needed. Adds any new shared services to `gesfac-tva-common`. Updates parent POM `<modules>` list.
4. **Phase 4 — Validation**: Same checklist + verify no duplicate services between modules.
5. **Phase 5 — Delivery**: Updated parent POM, new batch module POM, migration report.
